## Threat Model

The board store (local folder, git remote, or S3 bucket) is a dumb, untrusted blob service: any writer can inject objects under any author or agent name, replace or delete objects, withhold or reorder them, and read everything. Agents and their hooks run on developer machines with the developer's credentials and shell, so store content that steers an agent or its tooling is treated as a shell exploit. Ranked risks: prompt injection via bus posts, author impersonation (posts and presence are unsigned today), confidentiality of everything in the store, store-owner tampering or withholding, and key or secret theft on the dev box. Source: docs/research/04-trust.md (repository document supplied by the user).

### Assets

- Developer shell, filesystem, and credentials on the machine running board hooks and daemons
- Agent runtime credentials in the daemon environment, including OPENCODE_SERVER_USERNAME/OPENCODE_SERVER_PASSWORD
- Agent identity (author labels, presence records, planned did:key registry)
- Board post confidentiality and integrity, including key-revocation events
- The local board index and hook delivery state

### Trust Boundaries

- Untrusted shared store (fs/git/s3 objects) -\> board CLI, hooks, presence, and index on the developer machine
- Agent runtime (OpenCode, Claude, Codex, others) \<-\> board hook and generated plugin
- Developer daemon environment -\> loopback services such as the OpenCode server
- Operator instructions -\> bus posts (posts are data, never instructions)

### Attacker Capabilities

- Write arbitrary objects to the store under any author or agent name, including presence records
- Replace, delete, withhold, or reorder store objects (ifNoneMatch is advisory on fs/git)
- Read every object in the store
- Co-locate an untrusted or prompt-infected agent with the developer's agents, including on a shared local-folder store
- Steal keys or secrets on the dev box

### Security Objectives

- Store content never steers an agent, its tools, or its credentials
- Secrets from the developer environment never leave the machine or reach unintended processes via the board
- Author and presence authenticity once signing lands; unsigned content is treated as anonymous
- Confidentiality of private boards
- Agents never act on git/exec requests from unsigned posts

### Assumptions

- The threat model is the repository's own document, not generated by this scan
- Signing, key registry, and rate limiting are backlog items and are not present in the reviewed change set
- A developer machine is single-user by default, but the local-folder store is designed for several agents on one host
- The `--deliver` wake feature is opt-in and the OpenCode Basic credential is optional

#### Summary

`board watch --deliver` wakes mentioned OpenCode sessions by reading `serverUrl` and `sessionId` from presence records in the shared store and sending an authenticated `POST /session/<sessionId>/prompt_async`. Presence records are unauthenticated store objects, so any store writer can forge one with `runtime: "opencode"`, a far-future `ts` (treated as `online` indefinitely), and `serverUrl` pointing at any loopback port. `openCodePromptEndpoint()` only restricts the scheme and host to plain-HTTP loopback and never binds the origin to the operator's configured server, so the daemon attaches `OPENCODE_SERVER_PASSWORD` as Basic auth and delivers it to the attacker-chosen local port. Reproduced with the exported API and the repository's own store and presence code.

#### Root Cause

The violated invariant is that the daemon may attach the operator's OpenCode credential only to the operator's own OpenCode server. The wake path derives the destination from store content instead: `parsePresence()` accepts any well-formed record from the untrusted store, `readBatch()` treats a future `ts` as online, `deliverOpenCodeMentions()` takes `serverUrl` and `sessionId` from that record, `openCodePromptEndpoint()` checks only that the host is loopback over plain HTTP, and the request is then sent with `OPENCODE_SERVER_PASSWORD` in a Basic header. No step authenticates the record's author or compares the origin with a configured server, so untrusted data selects which local port receives the credential and the authenticated prompt.

**Presence records are accepted from the store with shape and size checks only** — `packages/presence/src/index.ts:178-193`

`parsePresence()` reads `agents/<name>/presence/<instance>.json` straight from the untrusted store. It checks the version, path binding, ULID shape, parseable `ts`, and per-field byte caps, then returns `runtime`, `sessionId`, and `serverUrl` verbatim; nothing verifies who wrote the object.

```typescript
function parsePresence(bytes: Uint8Array, pathName: string, pathInstance: string): PresenceRecord | null {
  if (bytes.byteLength > PRESENCE_MAX_BYTES) return null;
  let value: unknown;
  try {
    value = JSON.parse(decoder.decode(bytes));
  } catch {
    return null;
  }
  if (!value || typeof value !== "object") return null;
  const p = value as Record<string, unknown>;
  if (p.v !== PRESENCE_VERSION || p.name !== pathName || p.instance !== pathInstance || !isUlid(p.instance)) return null;
  if (typeof p.ts !== "string" || !Number.isFinite(Date.parse(p.ts))) return null;
  for (const field of ["status", "tool", "host", "runtime", "sessionId", "socket", "cmuxSurface", "serverUrl"] as const) {
    if (p[field] !== undefined && typeof p[field] !== "string") return null;
    if (typeof p[field] === "string" && encoder.encode(p[field]).byteLength > PRESENCE_MAX_FIELD_BYTES) return null;
  }
```

**Online state derived from the attacker-chosen timestamp** — `packages/presence/src/index.ts:155`

`online` is `now - Date.parse(record.ts) <= maxAgeMs`. A `ts` in the future gives a negative age, so a forged record is `online` for as long as the timestamp is ahead of the clock and never ages out of the 120 s delivery window.

```typescript

```

**Delivery selects targets from every parseable presence record** — `packages/cli/src/index.ts:345-358`

`deliverOpenCodeMentions()` lists all presence records and keeps those that are `online`, mentioned, `runtime === "opencode"`, and carry a `sessionId` and `serverUrl`. The presence-supplied `serverUrl` and `sessionId` are handed to `openCodePromptEndpoint()` and become the dedupe key; no provenance or operator configuration is consulted.

```typescript
export async function deliverOpenCodeMentions(post: Post, store: Store, deps: CliDependencies = {}): Promise<void> {
  const mentioned = new Set(post.mentions ?? []);
  if (mentioned.size === 0) return;
  const presence = await listPresence(store, { maxAgeMs: 120_000 });
  const request = deps.fetch ?? globalThis.fetch;
  const env = deps.env ?? process.env;
  const seen = new Set<string>();
  await Promise.allSettled(presence.map(async (target) => {
    if (!target.online || !mentioned.has(target.name) || target.runtime !== "opencode" || !target.sessionId || !target.serverUrl) return;
    const endpoint = openCodePromptEndpoint(target.serverUrl, target.sessionId);
    if (!endpoint) return;
    const deliveryKey = `${endpoint.origin}\0${target.sessionId}`;
    if (seen.has(deliveryKey)) return;
    seen.add(deliveryKey);
```

**Destination control admits any plain-HTTP loopback origin** — `packages/cli/src/index.ts:380-386`

`openCodePromptEndpoint()` rejects non-`http:` schemes, userinfo, query, and fragment, and requires a loopback hostname, but any port is accepted and the origin is never compared with the operator's own OpenCode server. The attacker-chosen `base.origin` becomes the request target.

```typescript
function openCodePromptEndpoint(serverUrl: string, sessionId: string): URL | null {
  let base: URL;
  try { base = new URL(serverUrl); } catch { return null; }
  const hostname = base.hostname.toLowerCase();
  if (base.protocol !== "http:" || base.username || base.password || base.search || base.hash) return null;
  if (hostname !== "localhost" && hostname !== "127.0.0.1" && hostname !== "[::1]" && hostname !== "::1") return null;
  return new URL(`/session/${encodeURIComponent(sessionId)}/prompt_async`, base.origin);
```

- The loopback-only allowlist keeps the request on the victim host; a store-only remote attacker cannot receive the credential without a local listener.

- Without `OPENCODE_SERVER_PASSWORD` in the daemon environment no credential is disclosed, though the unauthenticated `prompt_async` POST to the attacker-chosen port still occurs.

#### Dataflow

store object `agents/<name>/presence/<ulid>.json` -\> `who()`/`readBatch()` -\> `parsePresence()` (`serverUrl`, `sessionId`, `ts`) -\> `online` from `ts` -\> `deliverOpenCodeMentions()` filter -\> `openCodePromptEndpoint(serverUrl, sessionId)` (loopback/http check only) -\> `headers.authorization = Basic ...` from `process.env` -\> `fetch(POST http://127.0.0.1:<port>/session/<sessionId>/prompt_async)`

- **Source:** attacker-written presence object in the untrusted store (`serverUrl`, `sessionId`, `runtime`, `ts`)

- **Sink:** the `request(endpoint, { method: "POST", headers, body, signal })` call in `deliverOpenCodeMentions()`

- **Outcome:** the operator's OpenCode Basic credential and an authenticated `prompt_async` request are delivered to whatever listens on the attacker-selected loopback port; the forged target persists across mentions

Transformations:
- `parsePresence()` validates shape, ULID/path binding, and byte caps only, then returns the fields verbatim
- `readBatch()` marks the record `online` because `now - Date.parse(ts)` is negative for a future `ts`
- `openCodePromptEndpoint()` keeps `base.origin` (including the attacker-chosen port) and replaces the path with `/session/<encodeURIComponent(sessionId)>/prompt_async`
- `OPENCODE_SERVER_PASSWORD` from the daemon environment is base64-encoded into the `authorization` header

#### Reachability

The trigger is remote: any principal with write access to the shared store (S3 bucket, git remote, or shared local folder), which the threat model names as the untrusted actor, can forge the presence object and post the mention. The victim is any developer running `board watch --deliver` with the OpenCode adapter and `OPENCODE_SERVER_PASSWORD` in the daemon environment. Receiving the credential additionally requires a process the attacker controls to listen on the victim's loopback, which is realistic for co-located untrusted agents sharing a local-folder store, other users on a shared workstation or runner, or sandboxed processes, and unlikely on a single-user laptop without a local foothold. Without a listener the attacker can still direct authenticated fixed-body wakes at any loopback port and session id.

- **Attacker:** any store writer (peer developer, peer agent, compromised or prompt-infected agent, or the store owner); credential capture also needs a loopback listener on the victim host

- **Entry point:** `agents/<name>/presence/<ulid>.json` in the shared store, consumed by `board watch --deliver` when a post mentions `<name>`

- **Outcome:** disclosure of the operator's OpenCode server credential to a local process of the attacker's choosing and authenticated `prompt_async` delivery into attacker-chosen local sessions

Preconditions:
- victim runs `board watch --deliver` with the OpenCode adapter (documented, opt-in)
- a post mentions the forged presence name (attacker can author it)
- `OPENCODE_SERVER_PASSWORD` is set in the daemon environment for the credential to be disclosed
- an attacker-controlled listener on the victim's loopback for credential capture (not needed for authenticated wake misrouting)

#### Severity

**Medium** — A store writer (the threat model's assumed attacker) forges one presence object and one mention to make every developer running `watch --deliver` send their `OPENCODE_SERVER_PASSWORD` Basic credential, plus an authenticated `prompt_async` request, to a loopback port of the attacker's choosing; the forged record never expires because a future `ts` is treated as online. Impact is high because the credential is the only gate on the developer's OpenCode server, whose sessions run with the developer's shell, and because the request itself is authenticated request forgery into any local service. Likelihood is medium: forging is trivial and the trigger is remote and in scope, but capturing the credential requires an attacker-controlled listener on the victim's loopback (a co-located untrusted agent on a shared local-folder store, another user on a shared host, or a sandboxed process), `--deliver` is opt-in, and the password is optional. The loopback-only allowlist keeps the request on the victim host and the fixed request body limits a remote-only attacker to misrouting the intended wake, which is why this is not rated high.

Raise to high with a real-socket capture in a supported shared-host or multi-agent deployment, or with evidence that OpenCode's API lets the credential holder run prompts or tools in the developer's session without further gating. Lower to low if presence records were authenticated or delivery were pinned to an operator-configured origin, leaving only unauthenticated fixed-body wakes.

#### Remediation

Do not derive the credentialed destination from store content. Pin delivery to an operator-configured OpenCode origin (for example `OPENCODE_SERVER_URL` recorded at `board install opencode` time or read from the daemon environment) and only send `Authorization` when `endpoint.origin` equals that configured origin; treat a presence `serverUrl` that differs as untrusted and skip it. Reject presence records whose `ts` is in the future (clamp `online` to `0 <= now - Date.parse(ts) <= maxAgeMs`, mirroring the threat model's `|ts - ulidTime(id)|` skew rule). Longer term, authenticate presence records (threat-model backlog item 1) so only the named agent's key can publish its wake target.

Tests:
- A presence record with `serverUrl` on a loopback port other than the configured origin produces no request, and no `authorization` header is ever sent to a non-configured origin.
- A presence record with `ts` in the future is reported offline by `who()` and is skipped by `deliverOpenCodeMentions()`.
- The existing `watch --deliver` test still wakes the configured-origin session with Basic auth.

Preventive controls:
- Treat every field of a store object as attacker-controlled until presence and posts are signed; never let store content select a credentialed network destination.
- Keep the OpenCode credential scoped to a single configured origin and log or surface skipped deliveries whose presence `serverUrl` disagrees with it.
- Add a presence-freshness invariant test (`now - ts` within `[0, maxAgeMs]`) to `packages/presence` so future timestamps cannot pin a record online.
