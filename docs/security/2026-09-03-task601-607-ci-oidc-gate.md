## Threat Model

The store-centric repository threat model (docs/research/04-trust.md, authoritative, copied unaltered to 01_context/threat_model.md) is extended for this CI/IAM surface per the lead: the workflow authenticates to AWS via GitHub OIDC (no static keys), the provisioning script mints the IAM role, trust policy, and S3 grant, forked PRs must never obtain the token or assume the role, and the --delete path must never remove an IAM resource another principal still depends on and must fail closed on uncertainty. Fork-PR workflow code is untrusted; the provisioning operator and antstanley/bus main-push authority are trusted boundaries; third-party actions/images are trusted only at the exact pinned SHAs/digests.

### Assets

- AWS account IAM control plane: the GitHub OIDC provider (potentially shared with other roles), the CI role, and its trust/permission documents
- The CI test bucket: object containment under ci/\* and confidentiality/integrity of everything outside that prefix
- GitHub Actions workflow integrity and the short-lived OIDC tokens it can mint (id-token: write)
- Repository secrets (AWS_ROLE_ARN, BOARD_S3_TEST_BUCKET, AWS_REGION) and the invariant that no long-lived AWS credential ever reaches GitHub
- CI availability: runner-minute budget and bounded job lifetimes

### Trust Boundaries

- Forked PR workflows (untrusted code) \<-\> repository CI environment and AWS account
- GitHub OIDC token claims \<-\> IAM trust policy condition evaluation
- Provisioning script parameters (operator-controlled) \<-\> generated IAM policy documents and AWS CLI argv
- Third-party actions and container images \<-\> the runner executing them
- CI test objects under ci/\* \<-\> the rest of the bucket and account
- The provisioning operator's delete intent \<-\> shared IAM state that other principals may depend on

### Attacker Capabilities

- Open a pull request from any fork with arbitrary workflow/test content (runs under pull_request with no secrets, read-only token, and without the gated live job)
- Publish a malicious action version or mutate a floating ref/image tag (mitigated here by full-SHA/digest pins and --frozen-lockfile)
- Control every parameter of the provisioning script as its invoking operator, within IAM validation rules
- Create or modify IAM roles concurrently with the provisioning script's delete path (same-account principal) — the residual window behind the one reportable finding

### Security Objectives

- Only pushes of refs/heads/main in antstanley/bus can start the credentialed live AWS job or mint an OIDC token with id-token: write; forked PRs can never obtain the token or assume the role
- The CI role's trust policy matches exactly one repository+branch subject and one audience with StringEquals — no wildcards, no StringLike, no parameter-coerced broadening
- The inline S3 policy is least-privilege: ListBucket prefix-limited to ci/\*, Get/Put/Delete only on \<bucket\>/ci/\*, nothing account-wide
- Provisioning parameters cannot inject into IAM policy JSON or AWS CLI arguments; --plan performs zero AWS calls; every uncertain or error state on the delete path refuses deletion (fail closed); tag-owned resources only
- No secret material is ever printed by the script or the workflow, and no static AWS key lives in GitHub
- Every CI job runs under an explicit wall-clock bound

### Assumptions

- Write access to antstanley/bus main and the operator shell that runs the provisioning script are trusted boundaries
- GitHub issues OIDC tokens with aud=sts.amazonaws.com and sub=repo:\<owner\>/\<repo\>:ref:refs/heads/\<branch\> for push events; AWS verifies GitHub's TLS chain against its trusted root CAs (thumbprint optional)
- actions/checkout v6, oven-sh/setup-bun v2, aws-actions/configure-aws-credentials v6.2.3, and the minio/minio digest resolve to the official artifacts re-verified in this scan
- The aws CLI is the invocation path for the provisioning script (hard requirement at script line 98); its botocore response decoding behavior is part of the environment of record
- The delete path operates in a single-operator model (concurrent same-account IAM mutation is out-of-model; the one reportable finding documents exactly this residual)

## Open Questions And Follow Up

- After the first successful real apply, confirm in the AWS console that the role's trust policy, inline policy, and both tag sets match the documents this gate verified, and that the live job's first run assumes the role with the expected sub/aud claims.
- Address the single reportable LOW (cand-1) whenever the script is next touched: re-run the provider reference inspection immediately before delete-open-id-connect-provider and document the single-operator ordering assumption at the call site, in --delete --plan output, and in the README.
- The delete path's document parsing relies on the AWS CLI's botocore response decoding (after-call.iam policy-document decoding, verified in awscli 2.36.32). A future AWS CLI that stops decoding would flip this to fail-closed refusals, never unsafe deletions; if the script ever supports SDK-based invocation instead of the CLI, the URL-decoding normalization must be added explicitly.
- Consider a concurrency group (cancel-in-progress for non-main refs) in .github/workflows/ci.yml so rapid follow-up pushes do not queue redundant test/minio runs — hygiene only, no security impact observed this scan or in the first gate.
