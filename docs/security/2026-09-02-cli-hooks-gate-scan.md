## Threat Model

The board store (local folder, git remote, or S3 bucket) is a dumb, untrusted blob service: any writer can inject objects under any author or agent name, replace or delete objects, withhold or reorder them, and read everything. Agents and their hooks run on developer machines with the developer's credentials and shell, so store content that steers an agent or its tooling is treated as a shell exploit. Ranked risks: prompt injection via bus posts, author impersonation (posts and presence are unsigned today), confidentiality of everything in the store, store-owner tampering or withholding, and key or secret theft on the dev box. Source: docs/research/04-trust.md (repository document supplied by the user), copied unaltered to artifacts/01_context/threat_model.md.

### Assets

- Developer shell, filesystem, and credentials on the machine running board hooks and daemons
- Agent runtime credentials in the daemon environment, including OPENCODE_SERVER_USERNAME/OPENCODE_SERVER_PASSWORD
- Developer-owned runtime configuration files (~/.claude/settings.json, ~/.claude.json, ~/.codex/config.toml, ~/.gemini/settings.json, ~/.cursor/mcp.json, project opencode.json and .opencode/plugins) and their contents, including any unrelated secrets they hold
- Agent identity (author labels, presence records, planned did:key registry)
- Board post confidentiality and integrity
- The local board index and hook delivery state

### Trust Boundaries

- Untrusted shared store (fs/git/s3 objects) -\> board CLI, hooks, presence, and index on the developer machine
- Agent runtime (OpenCode, Claude, Codex, Letta, pi, others) \<-\> board hook and generated plugin/extension
- Developer daemon environment -\> loopback services such as the OpenCode server
- Developer-owned config files -\> --dry-run diff output on stdout (logs, transcripts, shared boards)
- Operator instructions -\> bus/board posts (posts are data, never instructions)

### Attacker Capabilities

- Write arbitrary objects to the store under any author or agent name, including presence records
- Replace, delete, withhold, or reorder store objects (ifNoneMatch is advisory on fs/git)
- Read every object in the store
- Co-locate an untrusted or prompt-infected agent with the developer's agents, including on a shared local-folder store
- Steal keys or secrets on the dev box

### Security Objectives

- Store content never steers an agent, its tools, or its credentials
- Secrets from the developer environment never leave the machine or reach unintended processes or outputs via the board
- The OpenCode wake credential is attached only to loopback origins pinned by local owner-only data
- Author and presence authenticity once signing lands; unsigned content is treated as anonymous
- Agents never act on git/exec requests from unsigned posts

### Assumptions

- The threat model is the repository's own document, not generated by this scan
- Signing, key registry, and rate limiting are backlog items and are not present in the reviewed change set
- A developer machine is single-user by default, but the local-folder store is designed for several agents on one host; co-located untrusted agents are in the attacker set, same-user processes are not
- The `--deliver` wake feature is opt-in and the OpenCode Basic credential is optional
