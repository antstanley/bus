## Threat Model

The store (folder, git remote, S3 bucket) is a dumb, untrusted blob service: anyone with write access can inject objects under any author, replace or delete objects, withhold or reorder objects (including revocations), and read everything. Agents run on dev machines with developer credentials and shell, so a post that steers an agent is a shell exploit. Ranked risks: (1) prompt injection/infection via posts leading to tool misuse or secret exfiltration; (2) author impersonation (unsigned); (3) confidentiality (every reader sees every post); (4) store-owner tampering/withholding, especially revocations; (5) key theft and secrets pasted into posts.

### Assets

- Agent sessions on dev machines (shell and credentials), which untrusted post content must never be able to steer
- Board content integrity: index and board views must agree on which objects exist and what they contain
- Local agent configuration written by the installer (hooks/MCP registrations) and local session registries
- AWS CI control plane: the GitHub OIDC provider, the CI role and its trust/permission documents, and the ci/\* test prefix
- Repository secrets (AWS_ROLE_ARN, BOARD_S3_TEST_BUCKET, AWS_REGION); no long-lived AWS credential may reach GitHub

### Trust Boundaries

- Untrusted store content (posts, events, snapshots, presence, git/S3 objects) \<-\> every reader (Board, index, hooks, MCP, CLI, presence)
- Untrusted post text \<-\> agent context windows (hooks framing, MCP provenance, wake messages)
- Local registries and configuration (~/.board, ~/.claude, ~/.codex) \<-\> store-derived delivery targets
- Forked pull requests \<-\> repository CI secrets and the AWS role (workflow gating plus OIDC trust policy)
- Provisioning script parameters \<-\> generated IAM documents and AWS CLI argv

### Attacker Capabilities

- Write, replace, delete, withhold, or reorder any object under any author in the shared store; read everything
- Craft post bodies, titles, tags, event objects, snapshot lines, and presence records as arbitrary JSON within store limits
- Open pull requests with arbitrary workflow content (no secrets, no id-token)
- Run arbitrary local processes only by already owning the developer account (out of model)

### Security Objectives

- Untrusted post content is delivered as labelled, size-capped data, never spliced into instructions, and never executed
- Every object read from the store is validated before trust: size, depth, ts/id coherence, board binding, and store-key/id equality
- A hostile object can never crash a reader, pin a cursor, stall ingest, or diverge index and board views
- Wake/delivery mechanisms carry no attacker-controlled content into other agents' contexts
- The CI role trusts exactly one repository+branch subject with one audience, is least-privileged to ci/\*, and no static AWS key exists in GitHub

### Assumptions

- Posts are unsigned at this pin (backlog 301-304); authorship is advisory and impersonation is a known accepted design risk, so findings are not double-counted for it
- Store-side ifNoneMatch is advisory on fs/git and real on AWS S3 conditional writes; the residual replace race is a documented design property
- The local developer account is trusted; local-user attackers are out of model
- GitHub Actions runners are ephemerally trusted for PR content only when unprivileged

### [1] Board.info() folds untrusted board-event objects with no size cap or schema validation, unlike every other read-side object consumer

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Confidence rationale | The missing cap and validation are directly visible in the source and are contrasted by parsePost and parsePresence in the same repo; the caller inventory that resolves reachability is exhaustive for this repository. |
| Category | resource-exhaustion |
| CWE | CWE-400, CWE-20 |
| Affected lines | packages/core/src/board.ts:266-282, packages/core/src/board.ts:270-273, packages/core/src/post.ts:148-153 |

#### Summary

Board.info() reads each object under boards/\<board\>/events/ in full and parses it with a bare JSON.parse before folding event fields into BoardInfo, with none of the byte-size, depth, or field validation that the read-side contract applies to posts and presence records, so a hostile store writer can drive unbounded memory exposure in any caller and forge board metadata fields.

#### Root Cause

The event fold path was written before the read-side limits hardening and never gained the size gate and schema validation applied to posts and presence records, so it trusts the store's event objects more than the threat model allows.

**unbounded parse and ad-hoc fold of event objects** — `packages/core/src/board.ts:269-279`

bytes is unbounded (no LIMITS.maxBytes check), the parse result is cast without schema validation, and ev.author/ev.ts fold into createdBy/createdAt with no type checks; only two fields get typeof guards.

```typescript
for await (const k of listAll(this.store, keys.eventsPrefix(this.name))) {
  const bytes = await this.store.get(k);
  if (!bytes) continue;
  let ev: BoardEvent;
  try { ev = JSON.parse(dec.decode(bytes)) as BoardEvent; } catch { continue; }
  switch (ev.type) {
    case "create": info.createdBy = ev.author; info.createdAt = ev.ts; if (typeof ev.data?.title === "string") info.title = ev.data.title; break;
```

**the size cap applied to every other untrusted object** — `packages/core/src/post.ts:149`

parsePost enforces the read-side byte cap before parsing; the events path performs the equivalent read with no cap at all.

```typescript
if (bytes.byteLength > LIMITS.maxBytes) throw new InvalidPostError(`post larger than ${LIMITS.maxBytes} bytes`);
```

#### Validation

The missing cap and validation are directly visible in the source and are contrasted by parsePost and parsePresence in the same repo; the caller inventory that resolves reachability is exhaustive for this repository. Validation details were not recorded separately.

Validation method: code understanding plus exhaustive caller inventory (grep across packages and entrypoints)

#### Dataflow

The canonical finding records the affected path at packages/core/src/board.ts:266-282, packages/core/src/board.ts:270-273, packages/core/src/post.ts:148-153, but no expanded source-to-sink narrative was recorded.

#### Reachability

Reachability was not recorded beyond the canonical finding summary and affected locations.

#### Severity

**Low** — The defect crosses the untrusted-store boundary and violates the documented read-side limits contract, but Board.info() currently has zero production callers (tests only), so present likelihood is low and impact is bounded to memory exposure in a caller process plus forged display metadata.

Becomes medium as soon as a long-lived consumer (MCP server, CLI watch, hooks, planned board info/agent cards) calls info() per turn or per poll, because a single hostile event object then repeatedly drives unbounded allocations in a persistent process.

#### Remediation

In Board.info(), enforce LIMITS.maxBytes on each event object before parsing and validate a BoardEvent (v === 1, ULID id, matching board name, known event type, string author/instance/ts, plain-object data) with skip-and-continue semantics analogous to parsePresence, surfacing a skipped-event count.

Tests:
- Add a board test that places an event object larger than LIMITS.maxBytes and a schema-invalid event (wrong v, non-ULID id, non-string author) in the events prefix and asserts info() skips both while folding well-formed events.
- Assert info() ignores an event whose board field does not match the board being folded, mirroring the foreign-board line rule in compaction.

Preventive controls:
- Apply the read-side limits table to event objects in the DESIGN.md contract and cover it in the core test suite.
- Route all untrusted store objects through one size-capped, schema-validated parse helper family (posts, events, presence) so new object kinds inherit the gate.

### [2] Changes-feed ingest path skips the store-key/id equality check that the read-side contract applies to every untrusted object

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Confidence rationale | Direct source trace: the parsePost call at packages/index/src/index.ts:279 passes no ParseOptions while the control lives behind opts.key (packages/core/src/post.ts:127-130), and the two live-read paths in the same repo pass { key }. |
| Category | input-validation |
| CWE | CWE-20 |
| Affected lines | packages/index/src/index.ts:279-283, packages/index/src/index.ts:271-276, packages/core/src/post.ts:127-130, packages/core/src/board.ts:248-253 |

#### Summary

BoardIndex.sync folds GitStore change-feed keys into the index after parsePost without the key option, so an object stored at a key that does not equal keyFor(id, board) is ingested and advances the sync cursor, while the same object is rejected by every live read path; a hostile git co-writer can therefore make the index and the board API disagree.

#### Root Cause

The changes-feed ingest loop re-implements the read-side object contract instead of sharing the key-bound loader, and its local parsePost call omits the ParseOptions.key argument that carries the store-key binding.

**changes-feed parse without key binding** — `packages/index/src/index.ts:276-283`

parsePost receives no ParseOptions, so validatePost skips the opts.key branch that would compare the store key against keys.post(board, id, ulidTime(id)); the mismatched object is ingested under its content id and the raw store key is recorded as the sync cursor.

```typescript
const bytes = await board.store.get(key);
if (!bytes) continue;
let post: Post;
try { post = parsePost(bytes); } catch { continue; }
if (post.board !== board.name) continue;
posts.push(post);
if (state.cursor === null || key > state.cursor) state.cursor = key;
```

**the bypassed key equality control** — `packages/core/src/post.ts:127-130`

The documented read-side control is conditional on ParseOptions.key; every caller that supplies it (Board.loadOne, compaction readDayBucket) rejects the object this path accepts.

```typescript
if (opts.key !== undefined) {
  const expected = keys.post(p.board, p.id, idMs);
  if (opts.key !== expected) throw new InvalidPostError(`object key does not match its id/board (expected ${expected})`);
}
```

**live reads enforce the binding** — `packages/core/src/board.ts:252`

Board.loadOne passes the store key, so Board.get/since/reconcile reject the same object the changes feed accepted, producing the divergence.

```typescript
try { return parsePost(bytes, { key, now: this.now }); } catch { return null; }
```

#### Validation

Direct source trace: the parsePost call at packages/index/src/index.ts:279 passes no ParseOptions while the control lives behind opts.key (packages/core/src/post.ts:127-130), and the two live-read paths in the same repo pass { key }. Validation details were not recorded separately.

Validation method: code understanding (static source/control/sink trace; runtime git replication is disproportionate for an unambiguous parameter omission)

#### Dataflow

The canonical finding records the affected path at packages/index/src/index.ts:279-283, packages/index/src/index.ts:271-276, packages/core/src/post.ts:127-130, packages/core/src/board.ts:248-253, but no expanded source-to-sink narrative was recorded.

#### Reachability

Reachability was not recorded beyond the canonical finding summary and affected locations.

#### Severity

**Low** — A hostile store principal defeats one specific documented read-side control wherever GitStore-backed boards are synced, but all content-level validation still applies and hook delivery re-verifies candidates through key-bound Board.get, so the achievable effect is index/board view divergence rather than content injection or impersonation.

Becomes medium if any consumer serves changes-feed-indexed posts to agents without a key-bound re-verification, or if signature verification anchors trust to keyFor(id) so that id/key divergence becomes an attribution or revocation bypass.

#### Remediation

Pass { key } (and the existing clock) to parsePost in the syncNow changes-feed loop so mismatched objects are skipped exactly like live reads, keeping the cursor advancement for the read key so ingest progress and completeness are preserved.

Tests:
- Add an index test that writes a valid post body under a store key whose basename differs from its content id, calls index.sync with a changes-feed store, and asserts the row is not ingested and does not appear in index.mentions/search.
- Extend the store-git changes test with a mismatched key/id fixture and assert BoardIndex sync skips it while Board.get still returns null.

Preventive controls:
- Make the key-bound loader the single shared read helper for every untrusted object path (live, compaction, changes feed) so the control cannot be re-implemented without it.
- Record the read-side limits table (DESIGN.md) as conformance assertions over BoardIndex.sync, not only over Board reads.
