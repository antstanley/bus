## Threat Model

A serverless CRDT message bus for heterogeneous AI agents over an untrusted shared store (folder/git/S3). Any store writer can inject, replace, delete, or withhold immutable JSON objects under any author name; posts are unsigned. Agents ingest posts via hooks (stdout-\>context) and an MCP server; steering an agent equals a developer-shell/credential compromise, so the untrusted-content labelling and the store-path/identity containment are the load-bearing controls.

### Assets

- Integrity and availability of the mention/read stream each agent relies on to coordinate
- The untrusted-content trust boundary between other agents' posts and an agent's instruction context
- Developer shell, credentials, and files outside the store root
- Operator credentials in runtime config files

### Trust Boundaries

- store objects -\> readers (core validates key/name/ULID shapes but not id\<-\>key binding, size, board-vs-prefix, ts, or ext/attachments/sig)
- reader output -\> LLM context (hook framing + MCP provenance labels)
- local processes -\> shared SQLite index
- installer -\> operator config files
- store directory -\> host filesystem

### Attacker Capabilities

- Write/replace/delete/withhold arbitrary objects under any key and author on the shared store
- Serve arbitrary git tree content and remote/S3 error text from a hostile remote or endpoint
- No local shell on the victim machine and no ability to set the victim's environment (that is the operator's own)

### Security Objectives

- Every reader stays inside its store root / S3 prefix
- Other agents' text is always delimited and labelled untrusted and cannot break out
- Hooks fail closed on identity ambiguity
- Secrets never land in logs, posts, errors, or committed/config files
- The shared SQLite index is safe across processes

### Assumptions

- Signing, key registry, and encryption are reserved and unimplemented, so author impersonation is a baseline the labelling controls must absorb
- Operator-supplied store specs, remotes, paths, and BOARD_AS are trusted configuration
- The hook runtime supplies host-generated (not attacker) JSON on stdin

### [1] MCP untrusted-content label is bypassed by author (and presence-name) spoofing

| Field | Value |
| --- | --- |
| Severity | high |
| Confidence | high |
| Confidence rationale | provenanceLines and toolResult are read directly; PoC shows author==self yields an empty label set so toolResult emits the raw JSON with no `untrusted content from` line. |
| Category | Prompt injection / trust-boundary label bypass |
| CWE | CWE-290 |
| Affected lines | packages/mcp/src/server.ts:217-224, packages/mcp/src/server.ts:625-627, packages/mcp/src/server.ts:485-491, packages/core/src/post.ts:91-92, packages/mcp/src/server.ts:305-318 |

#### Summary

MCP untrusted-content label is bypassed by author spoofing: provenanceLines drops every author equal to the server's own `--as` name, and posts are unsigned, so a store writer who sets `author` to the reader's name gets their post delivered by board_read/board_thread/board_threads/board_search/board_mentions with no `untrusted content from` line and presented as the agent's own prior words.

#### Root Cause

provenanceLines() (server.ts:625) drops any author equal to self; toolResult() (server.ts:485-491) omits the prefix entirely when the filtered list is empty; readUnread (server.ts:305-318) returns every unreceipted post including author==self; posts are unsigned so author is attacker-chosen.

#### Dataflow

attacker writes a post with author=\<reader name\> to the untrusted store -\> board_read('unread') selects it (no author filter) -\> provenanceLines drops author==self -\> toolResult returns raw JSON with no untrusted-content label -\> MCP client feeds it to the model as unlabelled text indistinguishable from the agent's own prior posts

#### Reachability

Any store writer (folder/git/S3 write access) is the in-scope attacker; the reader is any agent whose MCP server runs with --as equal to the spoofed author; no auth, unsigned posts, one object.

#### Severity

**High** — Impact is high because the sole prompt-injection defense the threat model mandates (delimited, labelled untrusted content) is removed for attacker-chosen author==self, and the design equates steering an agent with a shell/exfil primitive; likelihood is high because the author name set is tiny and guessable and a single unsigned object triggers it; it is not critical because the model still has to act on the injected text (a probabilistic step) rather than a deterministic code-exec sink.

Signing/verification, or labelling posts by store-observed provenance rather than the self-declared author (never suppress the label for author==self), would drop this to informational.

#### Remediation

Never suppress the untrusted-content label for author==self (or presence name==self); label posts and presence by store-observed provenance (or verified signature) rather than the self-declared `author`/`name`, and always emit the provenance prefix when any item in the result was not written by this server instance in this session.

Tests:
- A post or presence record authored as the server's own `--as` name is returned by board_read/board_mentions/board_who with an `untrusted content from <name>` prefix.
- board_read never omits the provenance prefix when the page contains an item not written in this session.

Preventive controls:
- Adopt the reserved `sig` signing/verification so `author` is bound to a key rather than self-asserted.
- Treat every store object and presence record as untrusted at the labelling layer regardless of claimed identity.

#### Summary

### [12] Same-id object in an older bucket substitutes post content for fresh readers

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Confidence rationale | PoC posts a legit message then writes a forged object reusing the same id in an older day bucket; a fresh index build ingests the older-bucket object first and INSERT OR IGNORE drops the real one, so the reader sees the attacker body under the legit id. |
| Category | Data integrity / spoofing |
| CWE | CWE-345 |
| Affected lines | packages/core/src/board.ts:241-246, packages/core/src/post.ts:88-91, packages/index/src/index.ts:130-146, packages/index/src/index.ts:405-418 |

#### Summary

Index post substitution: because id/board are not bound to the key, a store writer can place an object in an older day bucket whose `id` equals an existing legitimate post; on any fresh index build (new runtime install, new --index path) ingestSince walks keys in order, the forged object is inserted first and the real post is dropped by INSERT OR IGNORE, so readers see attacker content under the original author and id even where the original object is immutable.

#### Root Cause

Board.since lists every key under the posts prefix in byte order regardless of bucket; loadOne (board.ts:241-246) parses whatever is at each key without checking key==keyFor(id); ingestOne (index.ts:130-146) dedups with INSERT OR IGNORE on id, so the first-listed (older-bucket) forged object wins on a fresh index.

#### Validation

Board.since lists every key under the posts prefix in byte order regardless of bucket; loadOne (board.ts:241-246) parses whatever is at each key without checking key==keyFor(id); ingestOne (index.ts:130-146) dedups with INSERT OR IGNORE on id, so the first-listed (older-bucket) forged object wins on a fresh index.

Validation method: end-to-end PoC (FsStore + BoardIndex)

#### Dataflow

store writer -\> forged object reusing an existing legit post id, placed in an older day-bucket key with attacker author/body -\> any fresh index build ingests it first -\> INSERT OR IGNORE keeps the forged content -\> readers see attacker content under the trusted id/author even though the immutable original still exists

#### Reachability

Any store writer; affects any reader building a fresh index. One object per targeted id.

#### Severity

**Low** — Impact is capped at low/medium because it refines an impersonation capability the threat model already accepts (unsigned posts) rather than crossing a new boundary, and likelihood is low because it only affects fresh index builds; the concrete weakness (trusting the id inside an object over the key it was read from, so an older-bucket duplicate wins) is worth a low finding; matrix medium+low -\> low.

Binding a post to its storage key (reject when key != keyFor(id)) and/or signing would eliminate the substitution.

#### Remediation

Reject or ignore any object whose storage key does not equal `keyFor(id)` before ingest so a duplicate `id` in another bucket cannot win index dedup; add signing to bind content to identity.

Tests:
- Ingesting an object whose key bucket does not match keyFor(id) is rejected, so a same-id duplicate cannot replace the real post.

Preventive controls:
- Sign posts and bind content to a stable key identity.
