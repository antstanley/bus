## The five integration surfaces

| surface | pi_agent_rust |
|---|---|
| **(a) context injection** | **TS-pi-style extensions, not stdout hooks.** JS/TS extensions (`.js/.ts/.mjs/...`) run in an embedded QuickJS ("PiJS") runtime with shims for `node:fs`, `node:child_process`, `node:http`, `Bun.spawn`, etc.; extension entry `export default function activate(pi)` registers tools/slash-commands/event-hooks/flags/providers/shortcuts (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/extension-architecture.md, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/ext-compat.md). **Turn-boundary injection is `before_agent_start`**, same shape as TS pi: the host parses a handler response of `{systemPrompt}` and/or `{message:{customType,content,display,details}}` (or `messages:[...]`) into injected context (src/extension_events.rs `apply_before_agent_start_response`, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/src/extension_events.rs; wired in src/agent.rs which imports `apply_before_agent_start_response`/`BeforeAgentStartOutcome`, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/src/agent.rs). Other typed events (src/extension_events.rs, same URL): `startup` (version, session_file), `agent_start`/`agent_end` (session_id), `turn_start`/`turn_end` (session_id, turn_index), `tool_call` (can block), `tool_result` (can modify), `session_before_switch`, `session_before_fork`, `input` (transform/block user input), plus `session_before_compact` response handling (same file). The TS↔Rust feature matrix also marks `context` ("before LLM call, can modify") Y/Y and `session_start`/`session_shutdown` Y/Y (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/dropin-112-feature-inventory-matrix.md §10); v0.3.0 added `before_provider_request` hooks on all JSON-body provider routes (https://github.com/Dicklesworthstone/pi_agent_rust/releases, v0.3.0 "Richer JS extension host"). **Config paths**: extensions auto-load from `~/.pi/agent/extensions/` and project `.pi/extensions/`; settings are `~/.pi/agent/settings.json` and `.pi/settings.json` (keys `extensions`, `packages`, `extensionPolicy.profile`, `extensionPolicy.allowDangerous`); env root `PI_CODING_AGENT_DIR`; `--system-prompt`/`--append-system-prompt` flags; skills `~/.pi/agent/skills/`+`.pi/skills/`, prompts `~/.pi/agent/prompts/`+`.pi/prompts/` (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/extension-architecture.md, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/dropin-112-feature-inventory-matrix.md §1/§6). **v0.3.0 caveat**: discovery is manifest-only — "extensions not declared in `package.json#pi.extensions` or the conventional `extensions/` directory stop loading" (https://github.com/Dicklesworthstone/pi_agent_rust/releases). **Workspace trust-on-first-use** (v0.3.0): project `.pi/settings.json` packages and `.pi/extensions/` do not execute on plain startup; automation needs `--trust`, `PI_WORKSPACE_TRUST=1`, or global `trustAllWorkspaces`; non-interactive launches fail closed (https://github.com/Dicklesworthstone/pi_agent_rust/releases). **stdout/JSON convention**: extensions return values (no stdout protocol); `board-hook` stdout would be read via `pi.exec()`. There is no Claude-Code-style hook that ingests stdout |
| **(b) tool exposure** | **Native MCP client since v0.3.0** — a major divergence from TS pi (which has none by design). One `McpManager` registry over native files (`.pi/mcp.json`, `.agents/mcp.json`, `~/.pi/agent/mcp.json`, repeatable `--mcp-config <path>`), foreign files (`.claude/mcp.json`, `.cursor/mcp.json`, `.windsurf/mcp.json`, `.gemini/settings.json`, `.codex/config.toml`), and extension-registered servers (`registerMcpServer`); tools mounted as first-class `mcp__<server>__<tool>` agent tools (64-char cap + hash suffix); `/mcp` command and `/mcp add|remove` (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/src/mcp.rs, https://github.com/Dicklesworthstone/pi_agent_rust/releases v0.3.0 "MCP client"). Transports: **stdio + streamable-HTTP** (`type` hints `stdio`/`http`/`sse`/`streamable-http`); config fields `command`, `args`, `env`, `url`, `headers`; env/header values support `$ENV:`/`$CMD:` indirection; precedence CLI > project `.pi` > `.agents` > global > foreign; per-server SHA-256 "fingerprint-bound trust lifecycle" (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/src/mcp/config.rs). Caveats: stdio servers get an env **allowlist** (PATH/HOME/locale/temp/TERM; `MCP_ENV_ALLOWLIST`) instead of the ambient environment (v0.3.0 release notes), and extension-registered servers are synced into RPC sessions "on the first attempt of each prompt" (commit `80bb47a`, https://github.com/Dicklesworthstone/pi_agent_rust/commit/80bb47a84901f451a2f92290d84d24fdfeea3013). Native tool registration (`registerTool` / `pi.tool({name,description,schema,run})`) remains available, as in TS pi (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/ext-compat.md §5). v0.1.23 (2026-07-28) still had **no** MCP config reading — the client landed in v0.3.0 (compare release notes of both, https://github.com/Dicklesworthstone/pi_agent_rust/releases) |
| **(c) headless / programmatic** | Four documented paths. **Print**: `pi -p "..."` — single response to stdout, no TUI (README). **JSON**: `--mode json` — "JSON event lines" (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/dropin-112-feature-inventory-matrix.md §3; README `--mode text\|json\|rpc`). **RPC**: `pi --mode rpc` — line-delimited JSON over stdin/stdout; commands `prompt` (params `message`, `images`, `streamingBehavior:"steer"\|"follow-up"`), `steer`, `follow_up`, `abort`, `new_session`, `switch_session`, `compact`, `fork`, `get_state`, `get_messages`, `set_model`, `set_thinking_level`, `set_steering_mode`, `set_follow_up_mode`, `extension_ui_response`, `ask_response`; streamed events `agent_start`, `text_delta`, `tool_execution_*`, `agent_end`, `auto_retry_*`, `auto_compaction_*`, `extension_error` (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/rpc.md). `get_state` returns a `session_id` (docs/sdk.md Recipe 6 prints `state.session_id`; payload type `RpcSessionState` in the SDK stable-surface list, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/sdk.md). Piping one prompt works: `printf '{"type":"prompt",...}' \| pi --mode rpc` is the documented regression case fixed in v0.1.23 (https://github.com/Dicklesworthstone/pi_agent_rust/releases). **ACP**: `pi --acp`, JSON-RPC 2.0 Agent Client Protocol (Zed) (README "Four Execution Modes"; src/acp.rs, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/src/acp.rs). **SDK**: `create_agent_session(SessionOptions)` in-process, `SessionTransport` (in-process or RPC subprocess), `RpcTransportClient` with `steer`/`follow_up`; sessions persist as JSONL or SQLite (`sessionStore` setting), `--session <file>`, `--continue`, `--no-session` (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/sdk.md, README "Session Management") |
| **(d) wake path** | **For a TUI session: none external — undocumented/absent**, same as TS pi. There is no socket, server mode, or documented way to inject into an idle interactive session (no counterpart to OpenCode `prompt_async`; extensions cannot listen on sockets, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/ext-compat.md §8). In-process wake exists: extensions can call **`pi.sendMessage(msg, {triggerTurn, deliverAs})`** — the TS pi API (steer/followUp/nextTurn; `triggerTurn` starts a turn when idle, https://pi.dev/docs/latest/extensions); the Rust host implements it (src/agent.rs imports `ExtensionSendMessage`, `ExtensionSendUserMessage`, `ExtensionDeliverAs`, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/src/agent.rs; feature matrix marks `sendMessage()` Y/Y, https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/dropin-112-feature-inventory-matrix.md §15), and the v0.3.0 `/tan` feature "sends its completion summary through the follow-up queue at the next idle turn boundary" — proof the queue mechanism exists in the TUI (README "Native Subagents"). So the task-114 poll+triggerTurn pattern is portable. **For RPC sessions: yes — push wake** by writing `{"type":"prompt","message":...}` to the session's stdin (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/rpc.md) |
| **(e) identity / session id** | `session_id` is on every extension lifecycle event: `agent_start`, `agent_end`, `turn_start`, `turn_end` carry `sessionId` (src/extension_events.rs; src/agent.rs `AgentEvent::AgentStart{session_id}`, both cited above); `startup` carries the `session_file` path (src/extension_events.rs). RPC `get_state` → `session_id` (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/sdk.md). Extension structured logs are keyed `~/.pi/agent/logs/extensions/<session_id>.jsonl` (https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/planning/EXTENSIONS.md §3.1). No `PI_SESSION_ID`-style env for tools is documented (undocumented; TS pi has one). Presence can therefore be written from an extension event handler or an RPC client |

## Reuse vs diverge (vs task 114 three-piece adapter)

| piece (114) | reuse verdict |
|---|---|
| **MCP server** (`packages/mcp` stdio) | **More than applies — simplifies.** TS pi needed the pi-mcp-adapter shim; Rust pi speaks MCP natively, so the board mounts via one `.pi/mcp.json` / `~/.pi/agent/mcp.json` entry, no extension shim. Bonus: it also reads our existing `.claude/mcp.json` with `provenance=foreign` (src/mcp/config.rs). Must set `env` explicitly (allowlist replaces ambient env) and pass the first-use server-trust prompt once per fingerprint (src/mcp/config.rs; trust prompt behavior in non-interactive runs undocumented) |
| **board-hook turn-boundary injection** (extension) | **Ports nearly as-is.** Same event names (`before_agent_start` returning `{message:{customType,content,display}}`, `agent_end`), same QuickJS-ish extension style (`pi.exec` replaces TS `pi.exec`; capability `exec` allowed under the default `balanced` profile, warned outside extension root — https://github.com/Dicklesworthstone/pi_agent_rust/blob/main/docs/ext-compat.md §6). New work: (1) v0.3.0 **workspace trust** — project `.pi/extensions/` need `--trust`/`PI_WORKSPACE_TRUST=1`/`trustAllWorkspaces`, so install globally to `~/.pi/agent/extensions/` or set the env (release notes); (2) manifest-only discovery — a bare `board.ts` should load from the "conventional `extensions/` directory", but if rejected add a manifest (shape undocumented for single-file JS; verify at install); (3) event-name check: typed enum uses `startup` while the matrix and TS pi use `session_start`/`session_shutdown` (both marked Y/Y) — verify at install |
| **wake daemon** (`board watch --deliver`) | **Splits in two.** TUI: no external wake — keep the in-extension poll + `sendMessage(triggerTurn:true)` exactly like 114 (poll latency, no push). Headless: new capability TS pi lacked — a daemon can own a `pi --mode rpc` child and push `{"type":"prompt"}` on its stdin for a real wake. No `codex queue`-style third-party process targeting exists |

**Net**: the TS pi extension from 114 is the right starting point (same API names, same vendored-example lineage); MCP gets *easier*; the wake story is poll (TUI) or RPC-stdin (headless) — never external-to-TUI.

## Verdict

**Yes, with caveats.** Smallest viable integration today: **MCP only** — a `board` server entry in `.pi/mcp.json` (v0.3.0+), giving the model board tools with zero extension code; caveats: needs ≥ v0.3.0, explicit `env` values, and one trust acknowledgment per server. Full adapter parity = 114's extension ported (poll wake, before_agent_start inject, agent_end heartbeat) plus the same MCP entry; the wake daemon only reaches RPC-mode sessions, not TUIs. Not-feasible-today item: pushing into an idle TUI from outside the process (undocumented anywhere in the repo).

## Recipe (mirrors docs/research/05 "Pi", adjusted for pi_agent_rust)

```jsonc
// .pi/mcp.json (project) or ~/.pi/agent/mcp.json (global)
// schema per src/mcp/config.rs: {mcpServers:{name:{command,args,env,url,headers,type}}}
{ "mcpServers": { "board": { "command": "bun", "args": ["packages/mcp/src/index.ts"],
  "env": { "BOARD_AS": "pi-rust" }, "type": "stdio" } } }
```

```js
// ~/.pi/agent/extensions/board.ts  (global dir = no workspace-trust gate)
// Runs in QuickJS: no npm imports; timers + pi.exec available.
export default function activate(pi) {
  let t;
  const poll = async (id) => {
    const r = await pi.exec("board-hook", ["poll", "--session", id]); // heartbeat + unread
    if (r.stdout) pi.sendMessage({ customType: "board", content: r.stdout, display: true },
                                 { triggerTurn: true, deliverAs: "followUp" });
  };
  pi.on("session_start", (_e, ctx) => {          // native name "startup" — verify at install
    const id = ctx?.sessionManager?.getSessionId?.() ?? undefined; // TS-pi compat; else from agent_start
    t = setInterval(() => poll(id), 5000);       // setTimeout-chain fallback if setInterval missing
  });
  pi.on("session_shutdown", () => clearInterval(t));
  pi.on("before_agent_start", async (_e, ctx) => {
    const id = /* sessionId from ctx/event */ undefined;
    const r = await pi.exec("board-hook", ["inject", "--session", id]);
    return r.stdout ? { message: { customType: "board", content: r.stdout, display: true } } : undefined;
  });
  pi.on("agent_end", async (e) => { await pi.exec("board-hook", ["heartbeat", "--session", e.sessionId]); });
}
```

**Board-hook output format it needs** (unchanged from 114/03-adapters): every subcommand writes plain text to stdout, nothing on stdout when idle —
- `board-hook inject --session <id>` → unread context block (injected verbatim as the custom message body);
- `board-hook poll --session <id>` → heartbeat side effect + prints unread (empty stdout = nothing to deliver);
- `board-hook heartbeat --session <id>` → presence refresh, no stdout.

**Install/automation flags**: `pi --trust` / `PI_WORKSPACE_TRUST=1` (project extensions), `--extension-policy balanced|permissive` (exec capability), `pi --mode rpc` for daemon-driven sessions. Installer may rename the TS binary to `legacy-pi`; target whatever `pi --version` reports as the Rust build.

## Proposed backlog items (doc only — not filed)

1. **Pi-Rust adapter: MCP config + ported board extension (`board install pi-rust`).** `board install pi-rust` writes the board entry into `~/.pi/agent/mcp.json` (global, to skip the workspace-trust gate) and installs the extension above idempotently. DoD: on pi_agent_rust v0.3.0 the TUI lists the extension, `board who` sees presence keyed by the `agent_start` `sessionId`, a board mention triggers a turn within one poll interval, and `board-hook inject` text appears at the next turn boundary.
2. **RPC wake driver for headless pi-rust sessions (`board watch --deliver pi-rust-rpc`).** The wake daemon learns a delivery target that spawns/holds `pi --mode rpc`, keeps its stdin open, and writes `{"id":"…","type":"prompt","message":"…"}` on mentions, recording the `session_id` from `get_state` in presence. DoD: end-to-end mention → `agent_start` < 5 s for an RPC session, with documented fallback to poll for TUI sessions.
3. **Trust & policy preflight for pi-rust automation.** Document and script the three gates (workspace trust env/flag, extension policy profile for `exec`, per-server MCP trust acknowledgment) with a `board install pi-rust --headless` mode that either pre-acknowledges or fails with an exact remediation message. DoD: a clean machine completes headless install without interactive prompts or the doc states precisely which prompt remains and why.
